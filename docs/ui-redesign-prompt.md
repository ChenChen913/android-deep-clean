# 设计任务：为一款「Android 深度清理」工具的 HTML 报告重做界面

> 这份文档是完整的需求说明，可以直接作为设计任务的输入。文中的数字来自一台真实手机的真实扫描结果，请直接当作设计素材使用。

---

## 1. 产品是什么

一个跑在**电脑上**的 Android 清理工具（Python CLI + 脚本），通过 USB/ADB 连接手机，做四件事：

1. **只读扫描**手机存储（`/sdcard` 全盘 + 应用数据目录）
2. **交叉核对**系统媒体库索引（MediaStore）与文件系统实际文件
3. **产出清理候选**：分组、分级、附证据和删除影响
4. **执行后留档**：记录到底动了什么、验证结果、还能不能恢复

它不是手机 App，没有"一键加速"按钮。用户是在电脑终端里跑几条命令，然后**打开一个 HTML 文件看报告**，据此决定下一步。

报告是这条链路上唯一面向人的产物。它现在的问题不是功能缺失，而是**读不下去**。

---

## 2. 这份报告的核心价值观（比好看更重要）

这个工具与其他清理软件最大的区别是**不骗人**：

- 扫不到的地方就说扫不到，不猜
- 读不到的数字标"未知"，绝不写成 0
- 媒体库对不上就明说对不上，不说"媒体库是空的"
- 候选只给证据和建议，不替用户做决定

**所以界面的第一要务是"可信"，不是"有冲击力"。**

一个数字如果是估算值、是下限、只采集到一部分、或者根本读不到，界面必须让它**看起来就不一样**，而不是统一渲染成一个漂亮的大数字。

请把下面这五种状态当成**五个不同的视觉语汇**来设计，让人一眼能分辨：

| 语义 | 含义 | 举例 |
|---|---|---|
| 已知 | 完整采集，可以直接引用 | 文件扫描 11.35 GB |
| 部分 | 采到了，但只覆盖一部分，真实值更大 | 内部 data 1.2 GB（仅 3 个应用可读，是下限） |
| 未知 | 读不到，无法给出数字 | 内部 cache：未知 |
| 无法确认 | 有个结果，但证明力不足 | 媒体索引 0 条，但扫描看到 2 个同类文件 |
| 失败 | 明确出错 | 查询超时、权限拒绝 |

这是本次设计最重要的题目。**如果只能做好一件事，就做好这件。**

## 3. 需要设计哪几份报告

一共两个 HTML 页面，外加一个不需要设计的纯文本降级版（Markdown）。

### A. 分析报告 `report-before.html` — 主要设计对象

清理前的诊断报告。全程只读，**还没有删除、移动或隔离任何文件**。用户看完这份报告，才会决定要不要清理、清理哪些。

这是长文档：真机一次生成约 125 KB HTML，45 组候选，需要滚动很久。

### B. 清理结果报告 `report-cleanup.html` — 次要设计对象

执行完清理后的凭证。记录"已经发生了什么"：选了什么、删了什么、成功多少、失败多少、验证结果、隔离区还剩多少、能不能恢复。

气质应该像**手术记录/回执**，比分析报告更克制、更冷静。

两份报告要像同一套设计语言下的两个页面（一个"体检报告"，一个"手术记录"），不是两个产品。

**请把主要精力放在 A；B 给出同一语言下的版式示意即可。**

## 4. 分析报告必须承载的全部信息

下面按"用户看报告时的思路"组织，**页面顺序、分组方式、呈现形式由你决定**，但信息不能少。

### 4.1 这是谁的手机、这次分析是什么

设备型号（HONOR HLK-AL00）、Android 版本（10 / SDK 29）、设备序列号、分析 ID、生成时间、扫描到的文件数与总大小、整体覆盖率状态。

### 4.2 空间去哪了 —— 全报告最关键的一段

真实数据：

- 设备总容量 **128 GB**，已用 **79.59 GB**，可用 48.41 GB
- 本次扫描"说得清"的部分：**11.35 GB（占已用 14.3%）**
- **"说不清"的部分：59.21 GB（占已用 74.4%）**

这段的叙事核心是：**"你以为你知道手机里有什么，其实四分之三你不知道。"**

还需要一张表，列出各项来源，每项带三个属性：

- 大小（文件扫描 / 基础 APK / split APK / 应用内部 data / 应用外部 data / 媒体库声明大小）
- **统计口径**：这个数字是怎么算出来的（如"只读 `du`，含 cache/code_cache"）
- **范围**：覆盖了哪里（如"root/su 下按应用抽样，不是全量"）
- **与其他项的关系**：是否重叠 / 是否子集 / 是否不重叠

再加一组"为什么这些数字不能相加"的解释（比如：内部 data 包含 cache，cache 是它的子集；媒体库声明大小和文件扫描口径不同；APK 与文件扫描不重叠但与应用 data 可能重叠）。

### 4.3 扫描覆盖 —— 这次扫描可信吗

- 逻辑大小 vs 按 (设备, inode) 去重后大小 vs 目录数量
- 每个扫描根目录的状态：完整 / 部分覆盖 / 可疑 / 已扫描 / 跳过 / 未知，含原因
- 最大的 10 个目录（路径 + 逻辑大小 + 文件数）
- 覆盖限制说明 + 被跳过的路径列表

### 4.4 媒体索引核对 —— 相册里到底有多少东西

- 整体状态与原因
- 4 个集合（图片 / 视频 / 音频 / 下载）各自一行：索引行数 vs 文件扫描发现的同类文件数、状态、投影层级、尝试次数、说明
- 8 个统计项：索引条目数、声明大小、可解析路径数、范围内匹配率、范围内索引数、索引有扫描无、扫描有索引无、仅大小写不同
- 4 类差异的样本明细表（索引有扫描无 / 范围外缺失 / 大小不一致 / 扫描有索引无），每类最多 8 行
- 限制说明

集合状态有 6 种，视觉上必须能区分开：

- `ok` 正常
- `empty` 0 条，且文件系统里确实没有同类文件
- `zero_unconfirmed` 0 条，但扫描看到少量同类文件 —— **无法确认为空，也不算异常**
- `zero_mismatch` 0 条，但扫描看到不少同类文件 —— **明显异常**
- `failed` 查询失败
- `skipped` 跳过

注意 `empty` 与 `zero_unconfirmed` 的区别很微妙：前者是"确实没有"，后者是"我不知道有没有"。这正是第 2 节说的可信度问题。

### 4.5 应用级存储 —— 哪些 App 在吃空间

- 8 个统计项：应用数（293）、基础 APK（9.00 GB）、split APK（20.78 MB）、内部 data、外部 data（2.15 GB）、外部 media、外部 obb、已知合计
- 外部存储占用 Top 12 的应用，每行：应用名、包名、外部合计、data、media、obb、APK 合计、内部 data
- 未安装但目录仍在的包（卸载残留线索）
- 限制说明（内部 data 需要 root；split APK 有查询数量上限；基础 APK 可能不可读）

这里有个特殊点：某些值可能是"下限"（部分应用读不到），某些是"未知"（一个都读不到）。界面上不能都显示成 `0 B`。

### 4.6 跨轮目录变化（如果有上一轮数据）

新增 / 增长 / 缩小 / 消失 / 复活 / 疑似卸载残留 的计数，加 4–5 张明细表。首次分析时只有一句"已建立基线，下一轮开始显示变化"。

### 4.7 清理候选 —— 用户真正要操作的对象

概览：**45 组 / 6,407 个文件 / 1.04 GB / 44 组需要复核**

分类汇总（8 个分类，每行：组数 / 文件数 / 大小 / 最高风险）：

| 分类 | 组数 | 大小 |
|---|---|---|
| 旧截图 | 17 | 681.4 MB |
| 旧下载文件 | 5 | 287.0 MB |
| 缩略图缓存 | 3 | 65.9 MB |
| 应用缓存 | 12 | 27.7 MB |
| 重复文件 | 3 | 4.9 MB |
| 卸载残留 | 2 | 0 B |
| 聊天应用缓存 | 1 | 0 B |
| 空目录 | 2 | 0 B |

然后是**逐组候选**。每组需要展示：

- 风险等级：`SAFE` / `CAUTION` / `DANGEROUS`
- 标题（含路径，可能很长，如「旧截图：/sdcard/Pictures/Screenshots」）
- 大小（如 617.03 MB）
- 分类、动作类型（如 `clean_dir_children`）、置信度（0.00–1.00）
- **三段解释**，这是最有价值的部分，也是普通清理软件没有的：
  - **这是什么**：`应用 cache/code_cache/tmp 目录，通常可由应用重新生成。`
  - **为什么列出**：`缓存目录通常由应用自动重建，清理后不会删除账号、聊天记录或数据库。`
  - **删除影响**：`应用会重新生成缓存；不会删除账号、聊天记录或数据库。若含离线内容，需要重新下载。`
- 元信息：文件数、目录数、是否需要 AI 复核、是否可选
- 路径示例（最多 8 条，**非常长**，见下方样例）
- 证据列表（最多 10 条）
- 判断理由（最多 6 条）
- 保留建议（如果有）

真实候选样例（微信缓存，14.34 MB / 90 个文件 / 890 个目录 / CAUTION / 置信度 0.9 / 需要 AI 复核）：

```
路径：/sdcard/Android/data/com.tencent.mm/cache
示例文件：
/sdcard/Android/data/com.tencent.mm/cache/ThumbVideoCache/CdnDownload/Cache/appbrand0/008359244bddb5008538e0492b652b51.mark
/sdcard/Android/data/com.tencent.mm/cache/ThumbVideoCache/CdnDownload/Cache/appbrand0/008359244bddb5008538e0492b652b51.res
证据：
  路径：/sdcard/Android/data/com.tencent.mm/cache
  文件 90 个，目录 890 个
判断理由：
  缓存目录通常由应用自动重建，清理后不会删除账号、聊天记录或数据库。
  如果目录内包含离线下载/离线地图等大文件，清理后需要重新下载。
```

**关键设计难点**：45 组候选如果平铺成 45 个同样重的块，读者会放弃。需要让人在 10 秒内找到"最值得看的 3 个"（通常是：最大的一组、风险最高的一组、需要复核的一组）。

### 4.8 限制与安全边界

本轮所有限制的清单 + 4 条不可省略的声明：

- 扫描与分析全程只读，本报告不代表已经删除任何内容
- 候选必须经过 AI 复核、用户选择、确认令牌与执行前文件校验
- 媒体索引、应用级存储、目录档案只作为证据，不授权删除
- 本报告包含设备序列号与文件路径，分享前请自行脱敏

## 5. 清理结果报告必须承载的信息

- 整体状态：已完成 / 部分完成 / 已中止 / 已永久释放
- 模式：隔离（可恢复）/ 永久删除
- 元信息：设备、平台、传输方式、执行 ID、开始与结束时间、是否跑过验证、隔离区路径
- 数字卡：用户选择（组/文件）、成功文件、失败文件、处理逻辑大小、已释放空间、隔离区占用、可用空间变化（**带正负号**）、验证通过数/总数、累计永久删除、累计恢复
- 5 步流程说明：选择 → 执行 → 验证 → 隔离/释放 → 恢复
- 用户选择了什么
- 实际执行了什么 + 失败明细（失败的项**仍留在原位置**，这点要写明）
- 验证结果 + 异常明细
- 隔离区状态、purge 记录、restore 记录、可用空间变化记录
- 清理前发现了什么（候选分类汇总，简版）
- 剩余问题与下一步

一句话调性：这份报告是"我做了什么"的**证据**，不是"我帮你省了多少"的**成绩单**。有失败就要显眼，没验证就要说没验证。

## 7. 硬约束（不可协商）

1. **单文件、完全离线。** 一个 `.html` 双击就能看，不能发出任何网络请求：不能引 CDN、不能引 Google Fonts、不能引外部图片、不能引 JS 图表库。CSS 全部内联在 `<style>`；图形必须用**内联 SVG** 或**纯 CSS** 绘制；字体只能用系统字体栈（`-apple-system, "Segoe UI", "Noto Sans CJK SC", "Microsoft YaHei"` 这类）。

2. **手机必须好用。** 这是重点场景，不是"顺便兼容"。现状是表格用 `width: max-content` 强制横向滚动，手机上体验极差。请让主要信息在 375px 宽度下**竖着就能读完**，表格要么能优雅转成卡片/列表，要么只把次要列收进可展开区。

3. **浅色 + 深色都要。** 跟随 `prefers-color-scheme`，两套都要经得起看。

4. **全中文内容**，夹杂英文包名、文件路径、数字单位（`11.35 GiB`、`4,812`、`0.86`、`14.34 MB`）。

5. **超长文本必须优雅。** 文件路径可能 80+ 字符，包名、文件名、目录名同理。不能让一条路径撑破布局，也不能靠简单截断丢掉信息（可以让它换行、可以用等宽字体、可以折叠）。

6. **信息不能因为好看而丢失。** 所有字段都要有位置。可以折叠、可以降级为次要信息，但不能删。

7. **不依赖 JavaScript 也能读。** 可以用少量原生 JS 做增强（折叠、切换、平滑滚动、回到顶部），但不能出现"JS 挂了就白屏"。

8. **数据是静态渲染的。** 报告由 Python 模板直接拼出 HTML，不是前端框架，没有客户端数据绑定。所以不要设计成需要 fetch 数据才能显示的形态。

## 8. 视觉与交互：这部分由你决定，但请认真回答

### 8.1 现状的问题（供参考，不要被它框住）

- 所有区块长得一模一样：同样的白色圆角卡、同样的 24px 标题、同样的内边距。看三屏就开始疲劳。
- 几乎全是表格。整份报告只有**一条 10px 高的进度条**算得上"图"。
- 色彩是白底 + `#f5f5f7` 灰卡片 + 一个几乎没用到的蓝。语义色只出现在三个小圆角标签上。
- 关键数字（79.59 GB、59.21 GB、6,407 个文件）被塞进 14px 的小卡片，跟标签差不多重。
- 第一屏是标题 + 7 个小卡片，看完**不知道结论是什么**。
- 45 个候选块完全平铺，没有优先级引导。

### 8.2 我希望你建立的东西

- **一套有性格的色彩体系**：主色 + 中性阶 + 语义色。语义至少要能覆盖第 2 节的五种状态。现在这套太寡淡了。
- **一套有层次的排版**：不同重要性的区块，视觉重量要真的不同。不要所有区块都是同一张卡。
- **一套数字的表达方式**：大数字是这个报告的主角，让它有主角的样子。
- **一套"未知"的视觉语言**：这是这个产品的灵魂。斜纹、虚线边界、留白、问号标记……随你，但要成体系、要一致。

### 8.3 关于图表

现在整份报告只有一个细进度条。我希望至少有 **3 处真正的数据可视化**。

下面是我认为值得画的数据，**给你的是数据形态，用什么图由你判断**：

| 数据 | 形态特征 | 备注（可以推翻） |
|---|---|---|
| 已用空间 = 已知 11.35 GB + 未解释 59.21 GB | 部分-整体，且"未知"占 74% | 这里的主角是"不知道"，不是"知道" |
| 45 组候选 × 8 个分类的大小分布 | 长尾，第一类占 65%，后三类是 0 | 中文标签较长，注意排版 |
| 每组候选的 风险等级 × 大小 | 二维分布，45 个点 | 能不能一眼看出"又大又危险"的有没有 |
| 4 个媒体集合的"索引数 vs 扫描数" | 成对比较，差值很小或很大 | 重点是"对得上"还是"对不上" |
| 外部存储 Top 12 应用 | 排名，中文应用名 + 英文包名 | |
| 清理结果：成功 / 失败 / 跳过 | 类别少，但失败必须显眼 | 不要做成"全部成功"的庆祝图 |

请注意：

- **不要为了有图而给每个区块硬塞图。** 有些数据一张表就够了，硬画反而更难读。
- 图形必须**承载数据**，不是装饰。
- **"未知"不能被画成 0 或空白。** 它在视觉上必须是一个"有东西但不知道是什么"的状态。
- 环形图慎用：它天然掩盖"总量里有多少说不清"，而这份报告恰恰要强调这一点。

### 8.4 关于第一屏

我希望第一屏就能回答一个问题：**"这台手机什么情况，我该关心什么？"**

不是"欢迎使用本工具"，也不是七个并列的小指标。

### 8.5 关于长文档

6 个大区块 + 45 组候选，需要一种让人不迷路的导航。现在的做法是一条吸顶胶囊导航，手机上是横向滚动的，而且不指示当前位置。

### 8.6 关于情绪

读者是一个"手机空间不够、又不敢乱删"的普通人。他看到 59 GB 不知道去哪了会焦虑，看到"某个 App 缓存 14 MB"会觉得无聊。

界面要在**专业可信**和**不吓人**之间找平衡。不要做成 ICU 监护仪，也不要做成记账 App。

## 9. 明确不要做的事

- ❌ 不要做成一键清理 App 的营销落地页（大按钮、渐变光晕、"立即释放 5.2 GB！"）
- ❌ 不要用"进度环 + 百分比"把未知藏起来
- ❌ 不要把所有内容都做成卡片网格（现在就是这样，视觉噪声很大）
- ❌ 不要引任何需要联网的资源

## 11. 最后一句

这份报告的价值不在于"让 11 GB 看起来很壮观"，而在于**诚实地告诉用户另外 59 GB 不知道在哪**。

如果设计的结果让人感觉"这个工具什么都懂"，那它就是失败的。
如果设计的结果让人感觉"这个工具知道自己哪里不懂"，那它就是对的。
